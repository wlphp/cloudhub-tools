# CloudHub Tools 本地密钥环迁移设计

## 当前实现审查

- 本地密钥位于应用数据目录的 `.key` 文件，固定 32 字节。
- 凭据字段使用 AES-256-GCM；密文包含 12 字节随机 nonce 和认证后的密文，并以 Base64 保存到 SQLite。
- 数据库迁移包当前携带 SQLite 快照和 `.key` 字节，以保证跨机器导入后仍可解密；这意味着迁移包及导入前备份都属于高敏感文件。
- Rust command 不直接返回密文或密钥；账号/SSH/RDP/面板 Secret 只在需要执行厂商或连接操作时解密。

## 威胁模型与边界

当前方案主要防护“SQLite 文件单独泄露”或“日志/接口误记录凭据”，不能防护已经获得当前用户本地文件读权限并同时读取 `.key` 的攻击者。密钥环迁移可以降低密钥文件单独暴露和备份复制风险，但不能替代操作系统账户安全、应用目录权限和迁移包口令保护。

## 迁移决策

暂不直接替换现有加密格式，也不在未完成跨平台验证前新增 keyring 依赖。采用兼容的双读取、单写入路线：

1. 新版本首次启动时检测系统密钥环能力，不自动删除或覆盖 `.key`。
2. 已存在 `.key` 的用户继续使用旧密钥读取数据；在密钥环可用且用户确认后，将同一密钥安全写入密钥环，再保留可回滚的旧格式标记。
3. 校验密钥环读取、SQLite 解密和重新加密/写回均成功后，才切换为“密钥环优先、旧 `.key` 只读回退”。
4. 迁移失败、用户拒绝授权、无桌面会话或密钥环不可用时，继续使用旧格式并给出非敏感诊断信息。
5. 删除旧 `.key` 必须是独立的、明确确认的后续动作；迁移包导出必须明确提示其包含恢复密钥，不能静默改变现有导入格式。

## 平台适配与验收

- Windows：验证当前用户 DPAPI/凭据管理能力、锁屏后读取、权限拒绝和卸载/重装后的行为。
- macOS：验证 Keychain 授权提示、拒绝授权、应用签名变化和多用户隔离。
- Linux：验证 Secret Service 可用、无桌面会话、服务锁定和恢复失败；不能假设所有发行版都有同一后端。
- 所有平台：验证旧 `.key` 数据可读、迁移中断可恢复、密钥环条目不存在时不丢数据、导入包仍能在明确提供恢复材料后解密。
- 日志和错误中只允许记录后端类型、迁移阶段和错误分类，不得记录密钥环条目值、密文、密钥或凭据明文。

## 交付前阻塞条件

在 Windows/macOS/Linux 至少各有一套真实运行时验证，并完成回滚、备份和无密钥环降级测试前，不应把 `.key` 删除或把 keyring 迁移标记为完成。当前项目只具备旧格式加密、迁移包校验和失败回滚证据，尚未满足上述条件。
