# Codex 供应商切换与原生配置生成方案

日期：2026-10-23。状态：功能已实施，自动化验证通过；真实官方客户端兼容性仍需手动验收。

## 目标与决策

参考 Cockpit 的“切换 / 切换并启动”操作语义，将供应商配置生成从官方 CLI 的 config/batchWrite 改为 Rust 结构化编辑 TOML。保留 CloudHub 的加密备份、目录归属、OAuth 续期同步、模型目录、外部修改检查与恢复能力。

本次仅改造供应商启动链路。不扩展 OAuth 能力、协议转换范围或会话可见性修复，也不把账号管理中其他 CLI 调用一并替换。浏览器预览继续明确不支持这些原生操作。

## 可行性与取舍

改造前：provider_config::build_config 在临时目录启动官方 CLI AppServer，调用 config/batchWrite，再单独写入 model_catalog_json。ProviderLaunchDialog 已把应用和启动分开，主要需要统一按钮语义和强化状态校验。

选项一是保留 CLI，仅调整按钮，成本低，但供应商切换仍受 CLI 安装、初始化和 RPC 兼容性影响。推荐选项二：在现有 Rust 模块内使用 toml_edit 生成配置，移除这条配置生成路径对 CLI 的依赖。代价是项目自行维护字段兼容性，TOML 解析成功不代表官方客户端接受所有字段，必须实测。

当前 Cargo.toml 未直接声明 TOML 编辑库。实施时选择与现有 Rust 工具链兼容的 toml_edit 版本，评估必要的 Cargo.lock 更新，不做无关依赖升级。无需新增服务层或业务表。

## 交互方案

| 操作 | 行为 |
| --- | --- |
| 切换 | 校验目标、生成配置、保存恢复点、写入配置与认证、安装模型目录、更新绑定；成功后留在窗口 |
| 切换并启动 | 完成同一套切换流程后启动所选客户端 |
| 已切换同一选择 | 显示已切换状态；主按钮变为“启动 Codex”，验证磁盘配置后只启动 |
| 恢复配置与登录 | 显式恢复进入供应商模式前的配置与认证，保留现有冲突检测 |
| 启动失败 | 明确提示“配置已切换，启动失败”，允许仅重试启动或恢复 |

保持当前公共对话框及布局；点击遮罩不关闭。切换开关关闭时，按钮说明必须明确本次点击会启用切换，不能因改名隐藏写入行为。沿用运行中实例保护：默认客户端需要明确关闭确认，独立实例运行中禁止切换。

不能只依赖组件内 appliedSelection 判断已经切换：重新打开窗口、目标文件外部变化、供应商版本变化都必须重新核对。优先扩展现有 preview 返回不含密钥的绑定信息与磁盘匹配状态，必要时增加无凭据的选择签名；签名包含目标、供应商版本、密钥 ID、模型和 OAuth 账号 ID。

## 原生配置编辑规则

在 provider_config.rs 内以纯函数生成候选配置，再交给现有安装与备份路径写入。配置编辑全程留在 Rust，不返回带凭据的 TOML 给前端。

- 用 toml_edit 解析既有配置，保留未管理字段、其他 provider、MCP、工作区信任、注释与多行字符串，避免整份重建或字符串替换。验证格式保留的实际边界，不承诺生成文件字节完全不变；恢复仍使用原始快照。
- 仅更新 model、model_provider、model_context_window、model_auto_compact_token_limit、model_catalog_json、cli_auth_credentials_store 及 cloudhub_provider 下的本工具托管字段。该 provider 内的未知字段默认保留，可能冲突的认证或端点字段应显式处理，不能静默遗留或无差别清空。
- 上下文及压缩阈值为空时按现有语义删除对应托管键，不能写入 JSON null，也不能沿用上一供应商的数值。嵌套字段类型冲突、TOML 非法时中止并提示，不覆盖原文件；错误不得包含原配置片段或密钥。
- 客户端侧继续使用 wire_api=responses；Chat Completions 供应商仍写入本机网关地址和本机凭据。OAuth 绑定继续由 requires_openai_auth 与现有 auth.json 投影逻辑处理。
- 输出后再次解析并核对受管字段及模型目录路径。路径、URL 和字符串由库转义，不手工拼接。

## 写入与失败边界

沿用 AUTH_WRITER、文件权限、预览版本校验与供应商版本校验。顺序为：读取和验证目标 → 准备候选配置/认证/目录 → 写入前再次校验 → 加密保存恢复点 → 安装文件 → 提交绑定 → 如有要求则启动。

现有前端在已有备份时先恢复旧配置、再调用 apply，新配置失败时可能停留在已恢复状态。改造时应把该编排收回 Rust 命令内，并区分两个恢复目标：最初进入供应商模式前的恢复点，以及本次切换前的有效状态。不能将跨文件与 SQLite 操作当作天然原子事务；需用补偿写入及可恢复记录处理失败。

从供应商 A 切换到 B 时，成功后显式恢复仍回到最初的原配置；B 切换失败则尽量回到 A。若补偿失败，保留加密恢复信息并明确当前状态，禁止报告成功。实现前需核实可否复用现有快照结构，若必须新增持久字段再单独设计兼容迁移。

OAuth 已被客户端轮换时，先走现有归属和续期校验。启动失败不自动撤销成功切换。已有备份必须能被新代码读取和恢复。

## 实施拆分

| 步骤 | 执行层与主要文件 | 依赖、验收与风险 |
| --- | --- | --- |
| 1. 固定配置编辑契约 | Rust：provider_config.rs、Cargo.toml | 确认 toml_edit 版本与受管字段；覆盖注释、多行字符串、嵌套表、Windows 路径、无效配置；必要更新锁文件 |
| 2. 替换 CLI 配置生成 | Rust：provider_config.rs | 依赖步骤 1；无 CLI 时能生成配置；保留未知配置，空值语义正确，旧备份可恢复 |
| 3. 收拢切换与状态核验 | Rust：codex_providers.rs、现有备份与绑定模块 | 依赖步骤 2；验证 A→B 成功/失败、外部修改、OAuth 轮换、模型目录写入失败与补偿失败；不得丢失恢复点 |
| 4. 调整操作语义 | React：ProviderLaunchDialog.tsx；客户端：codex-providers.ts | 依赖步骤 3；统一按钮，重新打开窗口仍能识别状态，启动失败可仅重试启动；沿用公共弹层 |
| 5. 完成验证与审查 | Rust、React、桌面实测 | npm run build；cargo check --manifest-path src-tauri/Cargo.toml；针对性测试与无 CLI 桌面实测；检查凭据不进入日志、错误与前端响应 |

## 关键验收场景

1. 未安装 CLI、已安装 Codex 桌面客户端：纯 API 与 OAuth 绑定均可切换并请求启动。只解除供应商配置生成的 CLI 依赖，其他 CLI 专属能力仍按原要求处理。
2. Responses 直连、Chat 网关及聚合路径写入正确的端点与认证，模型目录可被实际客户端读取。
3. 切换不启动；切换并启动只触发一次；启动失败重试不会重复备份、恢复或更换凭据。
4. 配置含注释、多行字符串、已有 MCP/其他 provider 时保留；非法 TOML 与类型冲突时原文件不变。
5. A→B→恢复回到原始状态；B 应用失败回到 A 或给出可恢复的明确失败状态；外部编辑不被静默覆盖。
6. OAuth 轮换后恢复不重新使用旧凭据；旧版本加密备份仍兼容；错误不带配置原文或密钥。

## 实施与验证记录

- 已采用现有依赖树中的 toml_edit 0.20.2，锁文件只增加本应用的直接依赖引用；供应商配置生成不再调用官方 CLI。
- 保留现有公共弹层，以“切换 / 切换并启动”提供两条操作；后端返回不含凭据的选择信息，重新打开和重试启动时核对实际磁盘状态。
- 在现有加密备份内保存当前选择及未完成切换记录，不新增业务表。连续切换保留首次备份，失败回退到本次切换前状态；模型目录和版本戳一并补偿。中断后阻止继续切换和启动，用户可显式恢复。
- 同一目标可复用自己持有的 OAuth；其他实例、服务和供应商的占用保护保持有效。OAuth 认证冲突不隐藏预览和恢复入口，切换及启动仍执行严格校验。
- 自动化验证：npm run build；cargo check --manifest-path src-tauri/Cargo.toml；67 项供应商相关 Rust 测试；tests/ui/codex-providers.spec.ts 通过。覆盖 TOML 注释及内联表保留、非法配置、连续切换、补偿、事务回滚、进程中断、外部编辑、OAuth 续期及启动重试。
- 未使用真实账户修改官方客户端配置或执行真实启动验收。无 CLI 环境下的桌面端到端流程、实际客户端版本对模型目录的接受情况仍需手动验证；原生 TOML 编辑本身不能证明远端压缩、插件或其他 OAuth 能力可用。
