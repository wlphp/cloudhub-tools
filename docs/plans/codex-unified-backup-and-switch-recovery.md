# Codex 统一备份与认证切换修复方案

日期：2026-10-27（Asia/Shanghai）。状态：业务实现已完成；验证与交付结果见文末。

## 目标与范围

修复“目标已是 API Key 模式，旧 OAuth 绑定仍阻断切换和恢复”的问题。将账号切换与供应商切换使用的备份统一为一个历史列表，显示实际备份时间，允许选择记录恢复配置与登录。

“全局共用”指同一个 CloudHub 数据空间内，账号、供应商、默认客户端和独立实例共用备份模块与列表；记录必须按实际配置目录标识目标。不同目录不能相互套用备份。体验版与正式版仍保持业务数据库和加密密钥隔离，共同访问同一 Codex 目录时必须协调写入并识别外部变更。本方案不自动合并两版数据，也不默认开放跨版凭据读取。

仅备份本功能管理的配置、登录、模型目录及必要绑定信息，不复制聊天记录、工作区文件、MCP 工具数据或整个 `.codex` 目录。浏览器预览与手机端不新增桌面文件恢复能力。

## 已核实的问题

| 位置 | 修复前行为 | 后果 |
| --- | --- | --- |
| `core/paths.rs`、`core/codex/profile.rs` | 体验版和正式版使用不同 CloudHub 数据目录，默认 Codex 目录可相同 | 一端的绑定记录无法自动反映另一端的写入 |
| `commands/codex_providers.rs` 的 apply | 有备份时先调用 OAuth sync，再处理本次选择 | 选择纯 API 仍可能被旧 OAuth 绑定阻断 |
| `core/codex/provider_oauth.rs` | 有 OAuth 归属即要求磁盘和库存认证都通过官方 OAuth 校验 | 磁盘已经切到 API Key 时返回不适用的 OAuth 错误 |
| `commands/codex_providers.rs` 的 restore | 部分恢复路径仍须先完成 OAuth sync | 用于解困的恢复操作也可能被同一冲突阻断 |
| `commands/codex.rs` 的 install_profile | 按目录覆盖一条仅包含登录的备份 | 没有多版本历史，无法恢复当时被清理的第三方配置 |
| `core/codex/provider_config.rs` | 按目录保留首次配置备份与当前操作恢复记录 | 与账号备份割裂，缺少用户可选的历史时间 |
| `commands/codex.rs` 的 prepare_switch | 生成确认预览前可能先恢复供应商配置 | 用户尚未确认，文件就可能已经改变 |
| `core/codex/mod.rs` 的 AUTH_WRITER | 仅为进程内互斥锁 | 不能协调体验版、正式版两个进程对同一目录的写入 |

上述问题由现有源码及前一轮只读状态核查支持；不需要通过真实账号切换来再次制造冲突。

## 方案比较与推荐

| 方案 | 成本与复杂度 | 数据与安全边界 | 可逆性和验证 | 结论 |
| --- | --- | --- | --- | --- |
| 只修 OAuth 错误 | 低 | 可保留现有加密隔离 | 验证旧绑定与 API 切换；仍只有两套单份备份 | 可作为第一步，不能满足完整需求 |
| 统一历史模块与切换流程 | 中 | 复用本地 SQLite 加密；返回前端的仅为摘要 | 恢复前留新快照、操作可补偿；覆盖两种切换及历史恢复 | 推荐 |
| 两版共享业务库或在 `.codex` 保存明文历史 | 高，且破坏现有隔离 | 引入跨版密钥和敏感数据暴露问题 | 迁移与回滚范围扩大 | 不采用 |

## 统一列表与交互

1. Codex 顶部操作区增加固定的“备份与恢复”入口；账号区原恢复入口和供应商启动预览中的“恢复配置与登录”均打开同一组件。
2. 从供应商预览打开时，默认筛选当前目标目录；从全局入口打开时可看所有目标，并按目标、触发来源筛选。
3. 列表按备份时间倒序排列，列为：备份时间、目标、当时模式、账号/供应商摘要、备份原因、状态与操作。列表提供“立即备份”“恢复”“保留此备份”“删除”，空列表显示说明。
4. 时间存 UTC 毫秒并展示到秒，按用户本地时区格式化，悬浮显示时区和完整时间；时间相同以唯一记录 ID 稳定排序。
5. 原因包括：切换账号前、切换供应商前、恢复历史前、切回官方前、手动备份、旧版备份迁入。列表摘要描述被保存的状态；“本次准备切换到谁”另行记录，避免把目标账号误标成备份账号。
6. 选中记录后在同一弹层显示将恢复的目标、配置、身份、模型和依赖状态；点击“恢复此备份”进入现有公共确认交互。说明当前状态将先自动备份，完成后需重启 Codex；不自动启动客户端。
7. “恢复”成功保留原历史记录，同时新增“恢复历史前”记录，因此能够撤销这次恢复。恢复列表不应因使用过某条记录就把它删除。
8. 弹层复用 `OverviewDialog` / `SharedDialog`、`DialogHeaderActions`、公共样式、拖动和焦点管理；通过关闭控件或 Escape 关闭，点击遮罩不关闭。恢复/删除过程防重复提交。

模式摘要区分“官方 OAuth”“官方 API Key”“供应商 API Key”“供应商 + OAuth”“未登录”“外部配置/无法识别”。不能只看是否有 OAuth Token 就判断是否为官方上游。

## 备份内容与数据结构

在现有 SQLite 增加统一历史表 `codex_config_history` 和补偿表 `codex_config_operations`，由 Rust 内部备份模块管理。新表不加入跨设备云同步；数据库整包备份/导入沿用现有加密重封装流程覆盖新表。

记录元数据：唯一 ID、标准化目标标识、目标名称、来源、备份时间及其可信度、状态摘要、快照版本、内容指纹、保留标记、迁移来源。账号/供应商显示名进入隐私模式的遮罩规则，不向 UI 返回密文或任何凭据字段。

加密快照包含：

- `config.toml`、`auth.json`、CloudHub 模型目录及其版本元数据；分别记录“文件不存在”和“存在但为空”。
- 本目标相关的供应商、OAuth、独立实例绑定及恢复所需的身份标识。保存引用和必要的受控恢复信息，不复制业务库全部账号。
- 需要管理的网关逻辑设置；不把临时端口、进程 ID、命名管道当成可永久恢复的运行状态。
- 每个文件的捕获完整性；无法读取或校验捕获一致性时，不能创建一条声称完整可恢复的备份。

快照仍在 Rust 内使用既有加密工具和本应用密钥保存。文件读取有大小限制，拒绝链接和目标目录逃逸。前端列表只读取白名单摘要。

历史快照与未完成操作日志应有不同生命周期：历史供用户选择，操作日志用于写入补偿和崩溃恢复。可以复用现有 pending 设计，但不能用更新一条历史记录代替操作日志，也不能让清理历史删除未完成操作的恢复点。

建议默认每目标保留最近 50 条普通自动备份；首次完整备份、用户标记保留的记录、未解决故障的恢复点不自动清理。仅在新操作成功并且新备份持久化后做清理；手动备份默认保留。该数量为建议默认值，可在实施时沿用既有偏好设置方式调整。

## 修复旧绑定与跨进程冲突

先识别磁盘实际模式、身份和版本，再决定是否同步 OAuth：

| 当前状态和请求 | 处理方式 |
| --- | --- |
| 磁盘仍为同一 OAuth 身份，库存与磁盘存在续期差异 | 沿用现有归属和版本校验，把合法续期写回正确账号；不覆盖另一个身份 |
| 旧绑定存在，磁盘已变成 API Key；用户明确切换到纯 API | 先保存当前文件及旧关联的加密恢复点；候选配置校验通过后，在本次切换提交中解除过期 OAuth 投影，不要求当前 API 文件通过 OAuth 校验 |
| 旧绑定存在，用户选择新的 OAuth 身份 | 校验本次选择的账号完整性、独占归属和可用认证；先保存当前状态，再整体更新配置与绑定 |
| 只查看预览或启动，发现旧绑定与磁盘冲突 | 返回准确的冲突状态及恢复/重新应用入口；不静默改绑、不伪造“已切换”，不让通用 OAuth 校验错误遮蔽原因 |
| 用户明确恢复历史 | 当前模式校验错误不阻止生成救援快照；校验所选历史和恢复候选，成功后重建或解除当前关联，不依赖旧投影必须先同步成功 |
| 数据库、加解密、文件读取或写入失败 | 返回真实的受控错误，保留恢复点；不能把这些失败当成“旧绑定”直接跳过 |

所有会修改目标文件、关联或凭据回写状态的 CloudHub 路径，使用进程内锁及按真实目标目录划分的跨进程锁。体验版和正式版对同一目标使用同一个无凭据锁文件或等效操作系统锁；锁随进程退出释放，不以文件存在判断仍被占用。

跨进程锁不能约束官方客户端或其他工具，仍须检查目标进程是否停止，以及确认预览版本是否改变。预览到确认之间被另一端改写时，提示刷新并重新确认。目标路径标准化和大小写规则按操作系统处理，禁止通过别名绕过锁或串用备份。

旧版应用不会遵守新锁：在两版都升级前，不能承诺跨版并发写入完全受控；过渡验收应单端操作。方案不通过共享生产密钥来规避此问题。

## 统一切换与恢复顺序

账号切换、供应商切换、切回官方和历史恢复都进入同一目标级操作流程：

1. 预览只读取状态，生成有有效期的确认票据；不恢复供应商配置，不清理第三方配置，不写入登录。
2. 用户确认后获取目标锁，检查运行占用，重验票据、文件版本及相关账号/供应商版本；不一致时结束并要求刷新。
3. 构造并验证完整候选配置、认证、模型目录和目标关联；若历史引用已删除或无法解析，在写入前给出具体原因，不静默选择其他账号。
4. 读取完整当前状态并加密持久化历史备份和操作恢复记录。备份失败则不修改目标。
5. 使用现有私有权限和原子单文件写入能力安装文件，再事务更新本目标的数据库绑定；多个文件与 SQLite 不宣称天然原子，必须有补偿记录。
6. 回读验证文件、关联和模式，完成操作日志。失败则尽量恢复操作前状态；补偿仍失败时保留记录并标识“待恢复”，下次先处理该操作。
7. 刷新账号、供应商、预览和历史列表。切换已成功而客户端启动失败时，单独报告启动失败，保留已完成切换，允许重试启动。

恢复供应商快照时，要验证供应商/密钥引用及模型设置版本；需要本机网关的快照恢复逻辑设置并重新建立运行时服务，不能直接复用历史端口。依赖缺失时标记不可完整恢复并说明原因；不擅自复活已删除账号或供应商。

OAuth 历史备份不能保证旧令牌永远有效。恢复相同身份时，优先使用该身份已经合法同步的最新凭据，保持历史配置；不能用旧快照覆盖库存中的更新凭据，不能把磁盘不同身份的令牌写回原账号。无法构造可用登录候选时，在恢复前提示需要重新授权；不把“文件恢复成功”当成远端认证必定成功。

## 旧数据迁移

- 账号备份、供应商备份均迁入统一列表，保留来源和完整性。迁移应幂等，失败不删除旧表记录。
- 旧表没有创建时间，显示“旧版备份 · 原备份时间未知”，另存迁入时间；不能用迁入时间或数据库修改时间冒充原备份时间。
- 旧账号备份只有认证，标为“仅登录备份”；不得把当前配置拼进去伪装成历史完整配置。提供明确的仅登录恢复能力，但若与当前供应商模式冲突则阻止该组合并说明需要完整备份或重新切换。
- 旧供应商快照没有模型目录等可选字段时，保留“未捕获”的语义，不据此删除现有用户文件。已有 pending 操作先恢复其原有语义，不把半完成状态迁成可直接恢复的正常历史。
- 切换到新写入路径后，旧恢复入口统一转到新列表；保留旧数据直至迁移及恢复验证完成，不在同次升级里提前破坏旧恢复点。

## “切回官方”的定位

“切回官方”可以作为同一模块的快捷操作：选择已保存的官方身份或进入官方重新登录，备份当前状态，移除本工具管理的供应商接管及模型目录引用，再应用官方直连设置。

它与“恢复某个备份”含义不同。首次备份可能就是第三方配置，不能将任意首次备份标成官方配置。该快捷入口可以与本次统一流程一起实现，但不应成为绕过旧绑定缺陷的前置操作，也不能凭空恢复未保存的官方登录。

## 实施步骤与验收

| 步骤 | 执行层与主要文件 | 依赖 | 验收标准 | 风险控制 |
| --- | --- | --- | --- | --- |
| 1. 修复模式识别与旧投影处理 | Rust：`provider_oauth.rs`、`codex_providers.rs`、错误 DTO | 无 | 旧 OAuth 绑定 + 磁盘 API 时可完成显式 API 切换；同身份合法续期仍正常 | 以类型化状态区分冲突和底层故障，禁止笼统吞错 |
| 2. 建立目标级写入保护 | Rust：`profile.rs`、Codex 文件写入/同步入口 | 步骤 1 可并行设计 | 两个进程修改同一目标互斥；不同目标可分别操作；外部改写使票据失效 | 旧版不遵守新锁的限制需明确；锁覆盖回写与恢复 |
| 3. 实现统一快照与迁移 | Rust/SQLite：新 `core/codex/config_history.rs`、`database.rs`、`database_migration.rs` | 步骤 1、2 | 新快照包含完整受管状态，旧两类记录可幂等迁入、原时间未知正确显示 | 复用加密，明确局部快照，整包导入覆盖新表 |
| 4. 接入统一操作与恢复 | Rust：`codex.rs`、`codex_providers.rs`、`codex_instances.rs`、必要的新历史命令及注册 | 步骤 3 | 账号/供应商/实例/历史恢复共用备份流程；取消预览零写入；失败回到本次操作前 | 文件和 DB 故障注入，验证中断与补偿失败后可恢复 |
| 5. 接入公共历史列表 | React/TS：`CodexPanel.tsx`、`ConfigToolbar.tsx`、`ProviderLaunchDialog.tsx`、公共历史弹层及平台 client | 步骤 3、4 的 DTO | 两个入口看到同一数据；筛选目标，按实际时间选择恢复；恢复前备份可再次选回 | 复用公共弹层和现有 CSS；摘要不含凭据 |
| 6. 完成回归与交付 | Rust 测试、现有 Playwright Codex 场景与平台契约 | 步骤 1—5 | 下列关键场景通过；实际运行对应构建检查；记录真实客户端验收范围 | 不使用生产凭据或真实用户数据库作为测试夹具 |

重点回归场景：

- 官方账号 A → 供应商 API → 官方账号 B → 恢复任一完整备份，文件和账号/供应商/OAuth 关联一致。
- 体验版把共同目录切为 API，正式版仍有旧 OAuth 记录：预览准确提示，显式切换及历史恢复均有可执行路径。
- 连续切换保留多条时间记录；点击启动或刷新不产生重复备份；恢复前状态可以再次恢复。
- 取消预览、票据过期、外部修改、目标运行中、跨进程竞争均不产生部分切换。
- OAuth 续期、身份变更、已删除依赖、已失效历史凭据不会覆盖错误账号或伪造可用状态。
- 加密、文件安装、关联事务、模型目录、网关重建任一步失败及进程中断后有持久恢复记录。
- 旧账号与供应商备份迁移正确，时间不造假，缺失字段不补造；隐私模式和错误摘要无秘密值。
- 默认目录与独立实例互不串恢复；浏览器预览继续明确不支持原生操作。

实施后的必需检查：`npm run build`、`cargo check --manifest-path src-tauri/Cargo.toml`、相关 Rust 恢复/迁移测试及 Codex UI 流程；新增命令还须运行项目平台契约检查。真实客户端验证使用受控测试身份和隔离目标目录，不能仅靠模拟 invoke 断言实际可登录。

## 实施与验证记录

已完成的业务改动：

- `provider_oauth.rs` 区分旧投影冲突与同身份的正常续期。显式切换可替换旧投影；数据库或解密失败仍会中止操作。预览不再恢复或改写文件。
- `config_history.rs` 统一捕获受管文件和关联并加密保存，持久操作日志支持失败补偿和崩溃恢复；补偿遇到外部修改会保留恢复点。空文件与缺失文件分别保存，读取配置允许空内容，真正的认证读取仍拒绝空内容；失效绑定不用于标记备份的账号归属。
- 账号、供应商和实例切换，以及历史恢复接入统一操作。恢复前自动备份，保留所选历史；恢复 OAuth 优先使用同身份已保存的最新凭据，依赖缺失或绑定冲突会在安装文件前拒绝。
