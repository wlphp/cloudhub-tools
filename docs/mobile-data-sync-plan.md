# 桌面与独立 App 数据同步方案

日期：2026-10-02。状态：桌面与手机已有双向签名增量人工文件 UI；桌面到手机另支持一次性 LAN 发送，手机应用后可在同一限时会话自动回传签名 ACK，电脑验签并确认 outbox。若自动回执失败，手机仍可从 SQLite 恢复待回执并用系统文件保存器导出 `.chack.json`；电脑也保留文件导入回退路径。保留本机版本时会生成新的本地版本和待发 outbox 事件。版本/配置冲突会在应用事务内二次校验。双向 LAN 增量与签名回执已接入；可选中继、Android/iOS 真机验收和 iOS Xcode 构建仍未完成。
前提：手机与电脑均能独立直连云 API；同步可选，不依赖桌面在线来执行云操作。

## 建议路径

第一版实现局域网扫码配对、按账户选择共享范围、一次导入和手动增量同步。桌面可为已授权目标手机开启一次性 LAN 增量发送二维码；手机扫码后必须经电脑人工批准，并验证目标设备、批次签名和冲突后由用户确认应用。手机随后将签名 ACK 回传至原限时会话，电脑复核设备授权与签名后确认 outbox；回执失败仍可走加密/签名文件回退。手机也可向电脑发起一次性 LAN 增量推送；电脑逐次批准、预览并由用户确认应用后，签名回执沿原连接返回手机。若会话超时或断开，可用签名文件回退。
第二版增加可选的端到端加密同步中继，实现不同地点、不同上线时间的同步。
同步中继只保存密文和必要路由元数据，不持有云厂商凭据的明文，不执行云资源操作。
不愿部署或使用中继的用户，可以继续使用局域网同步或设备专用的加密导出包。

同步与云资源刷新是两个独立动作。电脑关机后手机仍使用已有本地凭据管理云资源；
关机后电脑中新产生不了更新，手机也不能取得电脑尚未上传的修改。

## 当前实现与缺口

### 持续增量同步的实施顺序

现有 outbox 和设备范围只是本机队列基础，不能直接当作可用同步协议。继续实现时按以下顺序推进，避免先开放网络接口再补授权：

1. **定义增量批次契约**：批次包含协议版本、源/目标设备 ID、批次随机 ID、起止序号、逐实体操作、稳定实体 ID、版本向量和删除标记；凭据只能由原生层读取并在形成批次后加密，React 不接触明文。
2. **发送端原生组包**：在单个 SQLite 读取快照中先验证目标设备仍 trusted，再读取其当前共享范围内的 outbox；每条 upsert 只取对应实体当前完整配置，delete 只取 tombstone。若同一实体积累多次变更，可合并成最新状态，但批次必须保留覆盖的 message ID，供接收端提交成功后逐条确认。批次上限按实体和字节数同时限制。
3. **接收端预览、冲突判断和原子应用**：先验证发送者信任、目标设备身份、签名、版本向量、实体类型与引用完整性；用户看到将新增、更新、删除和冲突的清单后确认。以稳定 ID 做幂等 upsert，在同一事务中更新本机版本向量、接收游标和已应用 message ID。并发版本不得按时间戳静默覆盖：可比较的版本自动应用，互不包含的版本进入人工冲突选择。
4. **签名回执与重试**：接收端仅在数据库事务提交后，以设备身份密钥对批次 ID、消息 ID 集合、接收设备 ID 和结果签名。发送端验证公钥绑定和签名后再写 acknowledgements；重复批次与重复回执必须幂等。撤销授权后，既拒绝新批次也拒绝迟到的回执。
5. **先局域网双向，后中继**：第一版由两端均可发起的短时局域网会话承载加密批次，桌面和手机都需批准对端身份，不能把现有“桌面单向发包”包装成双向同步。只有上述契约、事务和签名回执通过测试后，才增加云中继；中继只保存签名覆盖的密文包和最少路由元数据，不具备解密或云资源操作能力。

逐阶段验收：未授权/撤销设备、篡改签名、过期和消息 ID 重用会被拒绝；配置、inbox 去重和版本映射已在同一事务提交，失败会回滚。用户对版本冲突选择“使用收到版本”或“保留本机版本”；保留本机时会推进本机版本、创建反向 outbox 事件。桌面和手机均可人工发包、预览应用及导入签名回执；手机须先为目标电脑显式授权共享范围。身份不同却重复使用凭据/地址的配置冲突仍不能自动解决，必须先手动整理。桌面发往手机的 LAN 增量可自动回传签名回执；手机发往电脑的 LAN 推送与应用后自动回执已接入；回执失败仍可人工文件回退。中继、断网重试和设备间真机端到端验收仍未完成，因此还不能宣称完整自动同步。

发送端原生组包会在单一 SQLite 读取事务内获取 outbox、设备范围和实体配置快照。发送批次签名覆盖源/目标设备、序号、事件及凭据快照；接收端 `preview_sync_delta_bundle` 在原生层解密、验签并返回批次范围、删除清单、配置碰撞和向量时钟冲突，不回传凭据。`apply_sync_delta_bundle` 会在写事务内再次验证来源信任与批次签名，拒绝过期/并发版本和消息 ID 内容复用，并将配置、已应用消息、对端版本映射一起提交；若签名或落库失败，整笔事务回滚。事务成功后接收设备才生成签名回执，发送端仅在回执签名通过且消息仍属于该设备授权范围时确认 outbox。桌面到手机 LAN 增量仍需电脑逐次批准、手机确认应用；手机随后通过同会话 POST 回执，电脑重新检查当前信任、公钥签名和设备范围。会话最多维持五分钟/二十次请求，成功 ACK 后关闭；失败可回退到已签名文件。双向 LAN 推送与回执已接入，但需设备间端到端验收；尚无异地中继或冲突自动决策。

- 桌面 `core/crypto.rs` 使用设备数据目录中的 `.key` 加密本地秘密；手机端迁移到 Android Keystore/iOS Keychain 路径，但原生目标尚未编译验证。复制加密列到手机不能直接使用。
- SQLite schema v12 为云账号、托管主机和面板连接增加稳定 `sync_id` 与 outbox；schema v14 增加逐可信设备共享范围；schema v15 增加事务内远端应用保护；schema v16 增加带来源设备和唯一消息 ID 的 `sync_inbox`；schema v17 增加本机待回传签名回执表，已应用但尚未导出的 ACK 在 App 重启后仍可恢复，文件保存成功后才清除，设备身份轮换时清理。远端增量应用会将配置重新加密、已应用消息及对端版本映射放在单个 SQLite 事务；托管主机状态/指标及面板状态摘要等运行时字段不会触发同步事件。桌面和手机的双向签名增量人工文件交换 UI、签名回执生成/验证已接入；另支持桌面经一次性 LAN 二维码把增量送到指定可信手机，回执仍手动交换。
- `preview_sync_config` 可按选择的本地账户、托管主机和面板连接生成配置快照预览。DTO 不含云账户密钥、SSH 密码/私钥/口令、面板 API 密钥及运行状态；主机/面板关联使用账户 `sync_id`，而非本机 SQLite 自增 ID。该接口仅用于安全白名单与跨设备引用验证，不会打包凭据、写入接收端或发送网络数据。
- 加密配置包支持选择云账号、Linux SSH 托管主机和面板：桌面与手机均可选本机配置，生成独立口令加密的 `.chsync.json`；手机原生文件选择器负责保存包和签名回执；回执保存前校验本机签名，取消保存时 UI 保留待保存回执并允许重试。两端均可从文件选择器/文件输入接收配置，输入相同口令、先预览非秘密字段和目标设备冲突，再明确确认导入。若相同稳定 ID 已存在，接收端会更新该设备现有记录；不同稳定 ID 却复用凭据 ID、主机端点或面板地址时，禁用整批写入；确认时的 SQLite 事务再次检查冲突。Rust 内读取源设备密文并解密，再用独立迁移口令经 PBKDF2-HMAC-SHA256 派生密钥并以 AES-256-GCM 封装；包使用随机 salt/nonce、认证上下文、版本号和大小/迭代边界，不携带设备 `.key`。预览不含云密钥、SSH 密码、私钥、私钥口令或面板 API 密钥；接收设备使用本地密钥重新加密。SSH 主机指纹与运行状态不迁移，主机端点更新会清除目标端旧指纹。另支持经桌面批准的一次性 LAN 加密包接收；配对二维码附带桌面公钥身份，手机验指纹并登记来源设备，后续签名增量文件可复用此信任关系。
- Rust 同步加密路径使用 `zeroize` 清理命令收到的迁移口令、PBKDF2 派生密钥与中间块、加解密明文缓冲，以及解密后的云账号/SSH/面板配置对象；预览响应仍只克隆非秘密展示字段。
- 增量批次与回执均使用 Ed25519：批次签名覆盖规范化源/目标 ID 与完整批次 payload；接收端应用事务里重查 trusted 公钥并验签，降低撤销/换钥竞态。应用命令仅在事务成功后签署排序后的消息 UUID 集合；发送端 `acknowledge_sync_delta` 验证当前授权设备公钥与签名，再由 SQLite 再次确认消息仍属于该设备当前共享范围。
- 已实现局域网扫码取回迁移包：桌面用户选择实体并输入独立迁移口令后，Rust 原生层生成已加密 envelope，再启动最多 5 分钟、最多 20 次请求、一次成功下载即关闭的临时 IPv4 服务。二维码只承载私有 IPv4、随机 256-bit 会话 token 和固定路由；口令不进入 URL、二维码或网络。手机原生层以系统密钥对绑定令牌、设备 UUID 与六位核对码的请求签名；桌面验证签名后展示设备 ID/公钥指纹，用户确认并点击批准后先登记可信设备，再发送密文。拒绝、超时、无效签名或设备记录失败均不会下发。传输为局域网 HTTP，包体由 PBKDF2-HMAC-SHA256/AES-256-GCM 独立口令加密；会话元数据仍可被同网段观察。手机原生层只接受 RFC1918 IPv4、非特权端口和版本固定的 token 路径，接收大小限制 15 MiB；之后复用口令验证、冲突预览及用户确认导入。二维码流程要求至少 20 个 UTF-8 字节并建议使用随机高熵口令。iOS 已声明相机和局域网用途，macOS 已声明局域网用途；Android/iOS 真机网络授权和扫码仍待验证。此流程仍是一轮单向迁移，不代表双向持续同步。
- 加密包现在可重复用于人工同步：接收端按稳定 `sync_id` 新增或更新云账号、SSH 主机和面板；不同稳定 ID 却重复凭据 ID、主机端点或面板地址仍阻止整批写入。用户可选择是否带上源设备 tombstone；接收端会预览待删除的具体配置，并仅在用户确认整包后事务式删除对应稳定 ID，删除云账号时会解除主机/面板引用。默认不携带删除。历史包重放仍可能删除后来重新导入的同一稳定 ID，所以此机制只适合人工快照同步，不等同于具备因果检查的增量删除协议。更新会重置资源运行态；SSH 主机端点改变会清除本地指纹，要求重新确认。此文件包流程本身不带来源签名；桌面批准的扫码 LAN 流程已建立设备长期信任与撤销能力，但双端并发版本合并仍未实现；两端同时修改时，用户必须在预览后决定接受哪一份快照。
- schema v13 为本机设备行添加公钥绑定。Ed25519 私钥种子由 Rust 生成和派生公钥：Android 存入独立 Keystore 包装的 `noBackupFilesDir` 文件，iOS 存入 `ThisDeviceOnly` 且不参与同步的 Keychain 项；桌面用本机数据库密钥加密后保存在 SQLite preference 中。`get_sync_device_identity` 仅返回设备 ID 和公钥。检测到种子丢失时会先轮换设备 ID 并清理旧设备信任/同步游标，避免静默沿用身份；导入桌面整库时清除已导入的身份种子和公钥绑定。Ed25519 RFC8032 签名请求与绑定测试通过，Android target 已编译；iOS Swift 插件尚未在 Xcode 编译或真机检查。
- 桌面迁移面板现可查看可信设备的名称、UUID、状态、公钥指纹及可展开的共享范围（配置名称与稳定 ID），并显式撤销受信设备。列表不会返回凭据。撤销状态会使 outbox 分页读取与回执接口拒绝该设备；同一设备 ID 携带不同公钥不能覆盖原授权。schema v14 将首次人工批准时选中的稳定实体 ID 存入设备共享范围，分页与回执使用精确实体类型/ID 匹配；重新批准会在同一事务内替换范围。schema v15 为变更捕获触发器增加事务内远端应用抑制标记。撤销操作拒绝本机 ID，列表不返回公钥原值或私钥材料。真机 UI/安全键盘尚未检查。
- commands/database_migration.rs 的迁移包将 SQLite 快照与原始密钥一起写入，哈希用于校验，未提供独立包级保密保护；不能把现有 .chdb 作为远程密文同步包。
- 本机 SQLite 主键仍是设备内自增 ID；快照已把主机/面板关联转换为账户稳定 ID，导入时在目标数据库内重新映射。一次性迁移和签名增量均使用事务式导入；版本基线共享/初始化策略仍需在跨设备 UI 流程中验证。
- cloud_assets 是带 fetched_at 的缓存，云厂商才是状态和 DNS 配置的来源。
- 手机和桌面可双向生成、预览、应用签名增量并导入签名回执；手机可按设备设置本机共享范围，首次扫码后自动刷新目标电脑。双向 LAN 会话已接入；iOS 真机验证和冲突端到端验收仍未完成。手动快照文件仍是人工迁移路径，不提供增量消息重放保护。
- 手机系统整机备份不能充当换机方案：Android 默认可能备份应用数据库，iOS 的 Application Support 默认纳入备份，而设备绑定密钥不会随备份迁移。移动密钥插件源码现在显式排除 Android 云备份与设备到设备迁移，并在 iOS 启动时标记本地数据目录不参加系统备份；设备间迁移继续通过显式授权的加密迁移包/扫码流程。系统排除标记仍要在 Android/iOS 真机换机流程验证，不能视作绝对保证。

## 数据范围

| 数据 | 默认策略 | 原因及行为 |
| --- | --- | --- |
| 云账号配置、分组、备注 | 选中账户后同步 | 两端保持相同组织方式 |
| 云账户凭据 | 逐账户明确授权后加密同步 | 不向新设备自动共享全部凭据；必要时手机单独添加较小权限的凭据 |
| 管理主机、SSH 配置与指纹 | 选择性同步 | 指纹变化需要确认，不能静默替换信任记录 |
| SSH 密码/私钥、面板和云效令牌 | 单独选择共享 | 与普通配置分开授权；接收端能力不足时不导入 |
| 收藏、标签 | 同步 | 通过账户稳定 ID 和厂商资源身份定位 |
| 服务器状态、DNS 记录、面板指标 | 各设备从实际服务刷新 | 缓存可作首屏种子，但标注时间且不能覆盖新查询结果 |
| API 日志与操作日志 | 首版各设备保留 | 后续需要统一审计时，以设备来源追加汇总，不当作配置覆盖 |
| 证书元信息 | 可选择同步 | 证书私钥与 ACME 账号密钥默认不共享；申请任务保留在发起设备，避免自动重复签发 |
| FRP 配置 | 仅同步可移植模板 | 执行主机、本地路径和进程状态保持设备专属 |
| 桌面路径、窗口尺寸、下载目录、会话 | 不同步 | 不适用于手机 |

云 API 的启停、重启、DNS 修改、SSH 命令不写入同步队列。同步配置不能导致另一台设备重复执行这些操作。
手机不在原生沙箱可访问的主机，需要 VPN 等网络条件；同步 SSH 配置不会自动让内网主机可达。

## 第一次配对

1. 桌面用户解锁应用，进入“连接手机”，主动开启一个限时配对服务。
2. 手机原生层生成设备身份密钥；扫码读取配对会话 ID、连接地址和公钥/证书指纹，不扫描云账户秘密或桌面 .key。
3. 连接采用加密且绑定扫码身份的通道，两端显示校验短码与设备名称；桌面用户批准本次设备加入。短码用于校验，不当作加密密钥。
4. 桌面列出同步类别、账户和是否包含凭据，用户明确选择。首次默认只导入，不允许手机回写桌面；双向同步另外开启。
5. 桌面原生 Rust 层按所选记录解密并立即为目标设备重新加密传输；React 只取得数量、进度和结果。
6. 手机原生层验证发送者、记录版本与格式，解密后用手机自己的本地密钥加密落库，在事务中建立 ID 映射。
7. 手机确认导入完成，记录授权与同步基线；限时服务关闭，临时材料清理。后续同步继续使用已批准设备身份。

局域网方案需要电脑在线且两端网络可达，访客 Wi-Fi 隔离或系统防火墙可能阻止连接。
不直接放开已有 web-api.mjs 的监听地址；新增原生配对通道需明确权限、超时、连接次数与撤销行为。

## 密钥与授权分层

每台设备有独立本地存储密钥和设备身份。共享数据的传输密钥与本地数据库密钥分离。
建议每次同步批次生成随机内容密钥，使用成熟的认证加密保护数据；仅为被授权接收该批次的设备封装内容密钥。
普通配置与秘密分成不同批次，避免“能读取备注”等同于“能读取私钥”。
实现时选择成熟的密钥封装和签名库，固定经过验证的协议版本；例如评估标准 HPKE 封装机制。
设备签名、已批准的设备公钥、工作区/记录身份和版本一并验证，不能仅凭中继登录状态相信数据。

- 桌面延续 Rust 本地秘密存取边界，另行评估由操作系统安全存储保护本地密钥。
- Android 用 Keystore 中的密钥保护 App 数据密钥；iOS 使用适当访问控制的 Keychain 保存秘密材料。
- 云 Secret 通常是任意字符串，不能承诺全部成为硬件内不可导出的密钥；云 API 签名需要时仍会在受控原生内存中使用。
- 解锁和生物识别控制本机访问，不代替同步授权；云 Secret 不进入 React、日志、通知、剪贴板或未加密临时文件。
- 首版桌面是设备加入和共享范围的管理端，新设备不能通过中继自行取得授权；未来换主设备需要明确的授权转移。

### 移动端密钥保护实施契约

移动端必须通过项目自有的 Tauri 原生插件接入密钥库；前端只传入待加密/解密的数据并接收结果，绝不读取设备密钥。插件由 Rust 加密存储边界调用，不新增前端 `invoke` 暴露密钥的命令。Tauri 2 的 `PluginHandle::run_mobile_plugin` 可让 Rust 命令同步调用 Kotlin/Swift 实现，因此现有 `encrypt_secret` / `decrypt_secret` 调用方可保留 Rust 所有权，而无需把凭据处理移入 React。

工程约束：Tauri 官方移动插件结构要求插件 Rust crate 与原生 Kotlin/Swift 模块配套；该项目已获得用户同意更新 `Cargo.lock`，并已接入项目自有插件。不能通过普通文件密钥、前端可读密钥或未注册的原生源码绕过这一依赖关系。

- Android 当前实现：Keystore 持有不可导出的 AES-GCM 包装密钥，数据库密钥密文放在 `noBackupFilesDir` 的原子文件中，防止系统备份把不可解密的包装密文迁移到另一设备；尚待 Android 原生编译及真机验证。
- iOS 当前实现：Keychain 保存 32 字节数据库密钥，属性为 `AfterFirstUnlockThisDeviceOnly` 且关闭同步；尚待 macOS/Xcode 编译和真机验证。系统锁定、卸载重装、恢复备份及 Keychain 项丢失等生命周期需设备验收。
- Rust 统一暴露与现有同步函数一致的本地秘密接口。移动实现把 plaintext 和 ciphertext 仅在 Rust/Kotlin/Swift 原生进程边界内短暂传递；WebView 只接触账号表单本身与普通配置，不能获得密钥或已解密的数据库字段。
- 当前 `.key` 迁移会先把原 32 字节密钥写入系统安全存储、读回逐字节验证后再删除旧文件；密钥不变，因此 SQLite 密文无需重新加密。读取、写入或验证失败时旧文件保留且启动失败。该原生路径尚未跨目标编译与故障注入验证，真机验收前不得视为完成。
- 迁移包仍使用独立口令加密，不复用或导出系统密钥。新手机通过授权设备重加密导入，不能恢复另一台设备的 Keystore/Keychain 密钥；无可信设备时只能通过用户单独保管的恢复材料恢复。
- 需要补充原生插件的故障注入验证：密钥创建失败、密钥丢失、鉴权取消、设备锁定、密文篡改、数据库事务失败、旧密钥回滚和重复迁移；Android/iOS 均需真机验证。仅通过 TypeScript 构建或桌面 Cargo 检查不能视为移动密钥保护完成。

## 异地自动同步（可选）

桌面/手机在本机产生变更 → 原生层按接收设备加密并签名 → HTTPS 上传中继 →
另一设备上线后下载密文 → 校验身份与版本 → 本机解密、合并、重新加密落库。

中继需要身份认证、设备权限、配额、批次游标和保留策略，但不需要访问云 API。
中继可见设备上线时间、数据大小等元信息，端到端加密并不隐藏所有访问行为。
网络登录凭据与端到端解密材料分开；登录密码重置不能自动恢复已有密文。
中继可能丢包、回放或回滚，客户端校验签名和已见序号；签名不能单独证明“这是最新版本”。
首次加入授权不能仅依赖服务端可修改的设备列表。

App 打开时同步、修改后尝试上传、提供手动同步按钮；移动后台同步尽力执行，不承诺实时或持续驻留。
同一局域网可直接传输同一格式的批次；消息按唯一 ID 去重，避免局域网与中继重复导入。

## 记录模型与冲突

为可同步的实体增加 sync_id（UUID），保持现有本地 ID，通过映射表关联本地记录。
资源引用使用账户 sync_id + 厂商 + 地域 + 资源类型 + 厂商资源身份，不能用显示名称关联。
修改元数据包含工作区、实体 ID、消息 ID、来源设备、版本因果信息、删除标记与协议版本；
设备时间仅用于显示，不能凭 updated_at 或手机时间决定哪份数据获胜。

建议每记录维护设备计数的版本向量（只在授权设备范围内），据此区分新版本、旧版本和并发修改。
当前已实现双向人工文件交换；目标方案仍是短时双向局域网会话，不能将人工文件流程称为自动同步。

| 场景 | 处理 |
| --- | --- |
| 桌面修改分组，手机未改同一字段 | 合并到手机 |
| 两端改不同独立字段 | 基于共同版本逐字段合并；凭据相关字段视作原子组合 |
| 两端改同一字段 | 保留冲突，显示版本来源让用户选，不按时间静默覆盖 |
| 两端更换账户凭据 | 不显示秘密值，以设备来源和版本选择整组凭据；选择后重新验证账号 |
| 一端删除，一端修改 | 暂停该记录自动合并，提供删除或保留的明确选择 |
| 旧设备携带已删除记录重新上线 | 删除标记阻止复活；超过保留窗口的设备重新同步完整基线 |
| 重复上传、断网重试 | 消息去重；记录合并和本地队列写入使用事务 |
| 共享账户撤销 | 停止未来密文下发并同步撤销通知；不能假设离线设备立即清除其副本 |

本地修改与变更队列在同一事务提交，避免修改成功却没有同步记录。
账户删除处理关联配置，删除标记保留至有效设备确认或设备被撤销，不能短期直接清理。
手机独立执行云写操作前从厂商刷新相关状态；例如 DNS 修改可对比原记录，但能否条件写入取决于厂商 API。
端到端配置同步不能替代云资源并发控制。

## 换机、丢失与恢复

新手机：优先由已有可信电脑重新扫码授权，导入配置，再独立刷新云资源。
没有在线可信设备：可以使用用户保存的高熵恢复材料解密独立备份，并重建受信设备配置；
这是单独的恢复功能，不直接恢复旧手机硬件密钥或复制桌面 .key。
建议首版至少提供设备专用加密导出；后续再提供独立恢复备份。恢复材料不能和备份明文放在一起。

手机丢失：撤销同步设备授权、停止未来批次向它封装密钥，并撤销其服务会话。
这不会收回已经下载的云密钥和 SSH 私钥，也不能保证离线设备远程擦除。
要终止其直接操作云资源，必须到云厂商禁用/轮换凭据，SSH 删除授权公钥，面板等轮换令牌。
使用每设备独立、最小权限的云凭据与 SSH 公钥，可以缩小丢失设备的影响，但需确认厂商支持。

全部设备丢失且没有恢复材料：无法从只有密文的中继恢复秘密，只能重新录入或重新签发。
同步也不代替备份，因为删除和误修改同样会传播；需要单独的版本备份与恢复预览。

## 对当前项目的落地顺序

1. 明确首版共享数据白名单和账户选择规则；创建同步 UUID、关联映射与版本元数据迁移。（稳定身份、三类配置 outbox/tombstone、逐设备读取/确认接口、账户元数据快照及 schema v16 inbox 已实现。）
2. Rust 建立同步 DTO、校验、事务式导入导出和秘密重新加密，复用 repository 校验，不复用整库替换流程。（云账号/Linux SSH 主机/面板已实现加密导出包、非秘密预览、冲突检查、显式确认导入、目标端重新加密及桌面/手机人工文件传递 UI；删除传播为可选，接收端预览且用户确认后才会应用。）
3. 一次性 LAN 迁移已有桌面人工批准；扫码会把桌面设备公钥身份带给手机，配对后双方可验证签名；schema v14 将桌面授予手机的共享范围写入数据库。离线加密包作为局域网不可达时的换机迁移补充。
4. 桌面和手机双向签名增量文件预览/应用/回执 UI 已接入；桌面到手机 LAN 增量及自动签名回执已接入。手机到桌面 LAN 推送已增加桌面短时接收码、已信任设备签名申请、桌面逐次批准和分阶段正文上传，桌面接收后仍走既有口令/签名预览与用户确认；桌面确认应用后会通过同一限时连接返回签名回执，手机验证后确认 outbox；会话失败时保留签名文件回退。后续仍需真实设备端到端验收。
5. 再增加可选密文中继、设备撤销、异地同步和独立恢复备份。

验收至少覆盖：授权拒绝/过期、错误设备、篡改/回放、重复批次、断网、事务失败、不同设备自增 ID、
关联账户导入、凭据冲突、删除复活、设备撤销、换机、前后台切换和恢复材料缺失。
涉及 Rust/TS 实现时执行项目规定的 cargo check、npm run build，并在真实移动设备测试安全存储和网络权限。
