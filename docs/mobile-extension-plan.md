# CloudHub 手机端扩展方案

日期：2026-10-02。范围：代码盘点与选型建议，不是已实现的移动能力。

后续补充：用户正在评估“App 独立直连云资源”路线，其跨设备配对、凭据共享和同步方案见 [桌面与独立 App 数据同步方案](mobile-data-sync-plan.md)。下文常在线节点路线保留为另一种选项。

## 实施状态

已在 `src/mobile/` 增加独立 React 手机界面和 Android/iOS Tauri 配置；目前已实现多云账号本地管理、部分云资源/DNS/SSH、桌面批准的 LAN 首次迁移，以及桌面/手机双向的签名口令加密增量文件交换、共享授权和冲突决策。移动目标使用独立 Tauri 命令注册表，仅暴露当前 54 个移动端操作；contract 检查会阻止桌面命令意外加入移动白名单。桌面与移动前端均构建成功，Android ARM64 Release unsigned APK 已构建。手机首次启动会先排除当前与旧数据目录的系统备份，再迁移 `.key`；系统密钥确认可读且进入内存后，清理已复制的旧 `.key` 和 SQLite 文件，未迁移文件保留。Rust 与 Android/iOS 原生密钥桥接现在会清理可控的短期编码、解码密钥缓冲。仓库新增 macOS iOS unsigned archive CI workflow，用于验证 Swift 插件与 iOS Rust/Xcode 构建；该 workflow 尚未在远程 macOS runner 实际运行。系统密钥库插件与迁移代码已加入，但 iOS 工程编译、Keystore/Keychain 生命周期和双平台真机验收仍未完成；双向 LAN 自动回执已接入；可选中继仍待实现，进度以 [手机端 App 任务记录](tasks/active/task-20261002003942-手机端app实施支持双平台.md) 为准。

## 建议

完整移动运维工具优先选择 App；轻量查看、少量应急操作可以选择小程序。
在尚未确认用户规模、手机平台和凭据托管意愿前，建议以“个人或小团队、电脑关机后仍需管理”为规划假设。
当前用户已选择独立 App、手机直接管理云资源且不依赖电脑；实施路线为 Tauri 2 Android/iOS 原生客户端、本机凭据由系统密钥库保护，电脑仅在用户主动迁移/同步时作为可信数据来源。常在线管理节点和小程序不在当前交付路径。

## 当前代码证据

| 执行层 | 当前实现 | 对手机端的影响 |
| --- | --- | --- |
| 界面 | React 19、TypeScript、Vite；src/features 下有领域组件 | 类型、工具函数和业务语义可复用，窄屏流程需要重新组织 |
| 平台调用 | src/platform/clients/base.ts 的 invokeOrWeb、nativeOnly | 需要增加明确的移动原生或远程传输实现，不能把 Tauri 环境等同于桌面 |
| 云业务 | src-tauri/src/cloud 的多云实现，commands 中的资源操作 | 纯业务逻辑可提取；移动目标依赖兼容性仍需编译验证 |
| 原生耦合 | SSH 使用 State 会话，证书使用 AppHandle/事件，FRP 使用进程和本机路径 | 不能直接把全部 command 函数包装成公共接口 |
| 数据 | SQLite 与 core/crypto.rs 的 AES-GCM；密钥文件位于本地数据目录 | 没有现成跨设备同步；不能把数据库和 .key 文件直接当同步方案 |
| 浏览器预览 | web-api.mjs 监听 127.0.0.1；src/platform/api.ts 固定请求本机 | 手机访问桌面网页后，其 localhost 指向手机，不能自动连接电脑 |
| 预览安全 | web-api/core/security.mjs 主要检查 Origin/CORS | 不能把本地预览端口直接暴露成远程管理服务；需要独立身份和权限模型 |
| 移动入口 | lib.rs 已有 mobile_entry_point 标记 | 不代表当前能编译运行；updater 注册未按桌面条件隔离，Cargo 依赖却限定桌面 |

当前项目没有已验证的远程控制服务或移动构建。现有部分云厂商只提供读能力，手机端也应按厂商能力展示。

## 产品选择

| 维度 | 微信小程序 | App | 手机网页 |
| --- | --- | --- | --- |
| 进入方式 | 微信内打开，适合轻量入口 | 安装后使用，适合长期运维 | 浏览器打开，适合早期验证 |
| 现有 React/Rust 复用 | TS 模型可复用，Rust 业务放服务端；UI 需适配 | Tauri 有机会复用 React 和 Rust，需验证依赖 | React 与 TS 容易复用，Rust 业务需管理节点 |
| 云资源与 DNS 操作 | 适合通过受控管理 API 执行 | 可直连云 API 或连接节点 | 通过管理节点执行 |
| SSH 与文件管理 | 建议管理节点代理终端，终端体验需实测 | 可评估原生直连或代理终端 | 节点 SSH + WebSocket 终端 |
| 凭据存储 | 建议不下发长期云密钥，保存会话 | 可使用系统安全存储保护本地凭据 | 不保存云密钥，使用受控会话 |
| 私有部署 | 网络配置与平台发布条件需要提前验证 | 可设计成连接用户自己的节点 | 可连接自己的节点 |
| 交付成本 | 轻功能前端较轻，但仍有后端和平台发布工作 | 增加移动构建、签名、分发和设备验收 | 无应用商店构建流程，但需托管与鉴权 |

小程序并非不能实现终端，关键是代理服务、协议适配、键盘体验与生命周期；不以“绝对不支持 TCP”作为选型依据。
微信网络文档本次未成功读取，因此不在本方案承诺具体域名、类目、通知或审核资格。正式选小程序前需要用真实主体和部署域名验证。

## 三种执行模式

### 手机独立执行

App → 手机原生业务模块 → 云 API / SSH 主机。

不依赖电脑，不必增加管理服务器，最接近现有本地优先定位。代价是手机也要持有凭据，需系统密钥库、设备授权与跨设备迁移设计。
桌面文件路径、RDP 拉起方式、文件选择器需要移动实现。证书任务和连接不能依赖手机长期驻留后台。

### 手机遥控桌面

手机 → 安全网络或受控中继 → 桌面管理代理 → 云 API / SSH 主机。

凭据可留在桌面，但电脑关机、休眠、程序退出或断网就无法执行。适合个人辅助模式。
需要专门设计配对与可撤销授权；现有 web-api.mjs 不是这个代理。
手机不能运行桌面的 frpc，只能请求该桌面代理控制其所在机器的进程。

### 手机连接常在线节点（默认建议）

手机网页 / App → HTTPS 管理 API → 常在线节点 → 云厂商 / SSH 主机。

节点可以部署在用户自己的云服务器或常在线设备，第一版采用单用户部署，避免一开始引入公共多租户凭据托管。
手机关屏后，证书、资源同步等任务仍可在节点执行；电脑关机不影响手机管理。
代价是增加服务维护，并把可信凭据执行边界从个人电脑扩展到节点。
节点失陷会影响其被授权的云账户，应使用最小权限凭据和云厂商可撤销授权。

桌面第一阶段保留原有本地模式。新增远程节点模式后，桌面和手机查看同一节点数据。
节点数据与桌面本地数据不是自动一致；只能经过显式账户导入/授权或后续同步设计，不能共享挂载同一 SQLite 文件。

## 技术落地

1. 将云 API、SSH 协议、ACME 等纯业务与 Tauri State/AppHandle、UI 事件和文件选择器分开，按首版实际需要逐项提取。
2. 远程模式可评估 Rust + Axum 构建窄范围管理 API，优先复用已有 Rust 逻辑；具体依赖版本与实现另行验证。
3. 共享框架中立的 DTO、错误码、资源能力、分页与任务状态；HTTP 接口不要简单照搬 invoke 名字和任意参数。
4. 客户端增加本地原生/远程节点的传输适配；远程模式应显式配置节点，不能沿用预览环境自动判断。
5. UI 仍用 React + TypeScript。手机以搜索、常用资源、详情和动作菜单为主，避免压缩现有高密度桌面表格。
6. App 首选先验证 Tauri 2：登录、资源列表、一个写操作、文件选择、系统安全存储与前后台恢复。若关键移动插件或终端体验不达标，再比较 React Native；不预设迁移整个项目。
7. 如确定小程序优先，可考虑 Taro + React + TypeScript，共享契约和工具函数；现有 DOM/CSS/xterm 组件不能直接照搬。

## 最小安全与可靠性契约

- 节点模式：手机取得短期会话；首次设备授权、会话过期、设备撤销与二次认证在服务端生效。生物识别可保护本机会话，但不替代服务端授权。
- 原生模式：长期秘密用系统安全存储保护，禁止放 localStorage；桌面密钥文件不复制到手机。明确换机、撤销和丢失恢复策略。
- 远程 API：按账户、资源和操作授权；手机提交资源 ID 后由节点再次核验，不提供任意 invoke、shell 或路径执行入口。
- 长任务：返回 taskId，记录排队/运行/成功/失败/取消状态；弱网重试携带幂等标识。超时未知时先查结果，不盲目重放重启等动作。
- 私有节点：验证服务身份；内网主机只在明确允许的范围访问。同步缓存标注更新时间，离线允许查看缓存，写操作需要在线确认。
- 敏感导出单独授权。常规列表和日志不返回云密钥、SSH 密码、证书私钥或面板临时登录凭据。

## 分阶段交付和验收

阶段 0：确认个人/公开用户、Android/iOS、电脑关机要求、节点部署和凭据托管意愿；做选定云厂商的一条移动访问链路。
阶段 1：单用户节点与手机网页；资源列表、服务器状态、受控重启、DNS 查询与修改、只读面板状态。
阶段 2：任务管理、证书和流水线；加入 SSH 与文件操作，再交付 App。
阶段 3：告警与通知、节点上的 FRP 管理、跨设备偏好同步；只有明确需求后才建设多用户角色和公共服务。

每阶段验收覆盖授权拒绝、设备撤销、弱网和离线、前后台切换、重复提交、任务恢复、目标手机尺寸及敏感操作确认。
App 原生直连路线需增加真实 Android/iOS 的 Rust 编译、插件与 SSH 主机指纹验收。
没有移动构建和真机结果前，不承诺全量代码复用比例或工期。
